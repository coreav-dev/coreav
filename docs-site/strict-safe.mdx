---
title: "Strict-safe mode and the FFmpeg fallback"
description: "Run no FFmpeg code on files you did not make, or let coreav ffprobe and coreav ffmpeg hand the command lines CoreAV does not implement to the real FFmpeg."
---

`coreav ffprobe` and `coreav ffmpeg` take FFmpeg's command lines. CoreAV implements a subset of them. A command line outside that subset either goes to the real `ffprobe` or `ffmpeg` (the fallback), or is refused (strict-safe mode).

The fallback is on by default, so a script that calls FFmpeg keeps working. If your service reads files it did not make, such as uploads, turn on strict-safe mode. It is the only mode in which no FFmpeg code runs, in every build: CoreAV then never runs an `ffmpeg` or `ffprobe` program, not in place of a command line, not as a decoder and not as an encoder ([what strict-safe mode covers](#what-strict-safe-mode-covers)).

<Note>
The other commands (`probe`, `check`, `clip`, `split`, `join`, `remux`, `sanitize`, `extract-audio`, `extract-subtitles`, `chapters`, `decode-audio`, `hls`) never run FFmpeg, in either mode.
</Note>

## What strict-safe mode covers

In strict-safe mode CoreAV never runs an `ffmpeg` or `ffprobe` program, for any command and in any build:

| Where an `ffmpeg` program would run | What strict-safe mode does |
|---|---|
| In place of a command line that `coreav ffprobe` or `coreav ffmpeg` does not implement (the [fallback](#the-ffmpeg-fallback)) | Refuses the command line, with exit status 4. |
| As the decoder of `coreav thumbnail`, `coreav transcode` and the `libx264` command lines of `coreav ffmpeg`, in a build with the `ffmpeg-fallback` backend ([decoding through FFmpeg](#decoding-through-ffmpeg-in-builds-with-a-decoder-backend)) | Decodes with the build's other backends (`native-h264`, `dav1d`, `libvpx`). A video that only FFmpeg would decode is refused, with exit status 4. |
| As the encoder of `coreav transcode` and the `libx264` command lines of `coreav ffmpeg` | Encodes with an `x264` program only. `--encoder ffmpeg` is refused, and so is `--encoder auto` (the default) when no `x264` program is found (`COREAV_X264`, `--x264`, or `x264` on `PATH`), both with exit status 4 and before the input is read. |
| As the AAC encoder of `coreav transcode --audio aac` and the `-c:a aac` command lines of `coreav ffmpeg` ([encoding AAC audio through FFmpeg](#encoding-aac-audio-through-ffmpeg)) | Refuses them, with exit status 4 and before the input is read. A `-c:a aac` command line is never handed to FFmpeg; the fallback log records it with `not_run` `strict_safe`. |
| In CoreAV's internal decode worker and encoder launcher, which CoreAV starts in strict-safe mode when it is on, or which are run directly with `COREAV_STRICT_SAFE` set | The worker refuses the FFmpeg backend, and the launcher refuses a program whose file name, or the file it links to, begins with `ffmpeg` or `ffprobe`. An `x264` program named that way is refused before the input is read. |

On macOS (and Windows), the operating system cannot hold CoreAV's sandboxed worker and encoder to their memory budget, so strict-safe mode starts neither there: `coreav transcode` and the `libx264` command lines are refused before the input is read, and a video that only the `dav1d` or `libvpx` backend would decode is refused, both with exit status 4 and a message that begins `strict-safe: no enforceable memory limit for the sandbox on this platform`. The `native-h264` decoder runs inside the `coreav` process and still decodes there. Outside strict-safe mode the budget is advisory on those systems.

A default build, which the release binaries planned for 0.1.0 are, has no decoder backend, so only the first row applies to it. The `dav1d` and `libvpx` backends are C libraries of their own, not FFmpeg, and run in the sandboxed worker in strict-safe mode too.

To transcode in strict-safe mode, install an `x264` program and use a build whose backends decode your sources: `native-h264` for H.264, `dav1d` for AV1, `libvpx` for VP8 and VP9 ([build features](/build-features)). The audio can be copied, dropped, or encoded to Opus in a build with the `libopus` feature; CoreAV has no AAC encoder of its own, so `--audio aac` and `-c:a aac` are refused.

## Turn on strict-safe mode

Set the environment variable or pass the flag:

```sh
export COREAV_STRICT_SAFE=1
coreav ffprobe -v error -show_format input.mp4

coreav --strict-safe ffprobe -v error -show_format input.mp4
```

- Any value of `COREAV_STRICT_SAFE` other than empty or `0` turns the mode on, so a mistyped value fails closed.
- Under a link named `ffprobe` or `ffmpeg` that points to `coreav`, every argument belongs to the tool. Only the variable works there.

## What a refusal looks like

In strict-safe mode, a command line that CoreAV does not implement is refused by name, with exit status 4:

```console
$ coreav --strict-safe ffprobe -v error -show_data -show_packets input.mp4
coreav ffprobe: option '-show_data' is not supported: packet payloads are not printed
$ echo $?
4
```

A refusal can come after the input is opened, for example for a source with chapters, an output file that already exists, or a value such as `-crf 90`. No refusal writes or changes the output. A program that gets exit status 4 can send the job somewhere else, or reject it.

`coreav thumbnail` and `coreav transcode` refuse with exit status 4 too, and print a `coreav.error/1` object whose message says what to change. Here, in a build whose only decoder backend is `ffmpeg-fallback`:

```console
$ coreav --strict-safe thumbnail input.mp4 -o thumb.jpg
{"kind":"unsupported_feature","limit":null,"message":"strict-safe mode never runs the ffmpeg program, so it cannot decode the h264 video, and no other decoder of this build does: build coreav with the native-h264 feature, or run without --strict-safe and COREAV_STRICT_SAFE (no decoder for h264: nvdec: not available; native: not available; dav1d: not available; libvpx: not available; ffmpeg: unsupported: not run in strict-safe mode)","offset":null,"schema":"coreav.error/1"}
$ echo $?
4
```

A refused encoder (`--encoder ffmpeg`, `--audio aac`, or no `x264` program) is refused before the input is read. A refused decoder is refused once CoreAV has read the container and before any frame is decoded. Neither leaves an output file.

## The FFmpeg fallback

Without strict-safe mode, a command line that CoreAV does not implement runs the real program instead. That program is FFmpeg's C code, and CoreAV's limits and checks do not apply to it. CoreAV says so in one line on standard error, at every log level, `-v quiet` included:

```console
$ coreav ffprobe -v error -show_data -show_packets -of csv input.mp4
coreav: ran /usr/bin/ffprobe instead (not native: -show_data)
packet,video,0,0,0.000000,...
```

Standard output is the program's, byte for byte, and so is the exit status. On Unix CoreAV replaces itself with the program, so its process id and signals are FFmpeg's too.

### Which program runs

1. If `COREAV_FALLBACK` is set, it names the program. A directory names its `ffmpeg` and `ffprobe` (with `.exe` on Windows). A file names that one program. If the path does not exist, cannot run, or names the other tool, nothing runs: the refusal stands, with exit status 4 and a line that names the variable and the reason.
2. Otherwise CoreAV runs the first `ffmpeg` or `ffprobe` on `PATH` that it can run and that is not `coreav` itself.
3. If there is none, the refusal stands, with exit status 4.

### What is never handed on

Only a refusal goes to FFmpeg. These keep their own exit status and never reach FFmpeg:

| Exit status | Meaning |
|---|---|
| 1 | CoreAV rejected the file. Handing it on would send FFmpeg exactly the files the checks stopped. |
| 2 | The command line is malformed. |
| 3 | An input cannot be read, or an output cannot be written. |

### Log the commands that were not native

Set `COREAV_FALLBACK_LOG` to a file path, and CoreAV appends one JSON line for each command line that was not native, whether FFmpeg ran it or CoreAV refused it:

```json
{"args":["-v","error","-show_data","-show_packets","-of","csv","INPUT"],"coreav":"0.0.1","ran":"/usr/bin/ffprobe","reason":"-show_data","time":"2026-10-30T00:51:20Z","tool":"ffprobe"}
{"args":["-i","INPUT","-vf","VALUE","OUTPUT"],"coreav":"0.0.1","not_run":"strict_safe","ran":null,"reason":"-vf","time":"2026-10-30T00:51:20Z","tool":"ffmpeg"}
```

File names, URLs and option values become placeholders (`INPUT`, `OUTPUT`, `VALUE`), so the log holds nothing private and you can share it. Only option names and values that FFmpeg publicly lists are kept. When nothing ran, `ran` is `null` and `not_run` says why: `strict_safe`, `no_program`, `fallback_unusable` or `recursion_guard`. A log that cannot be written costs one line on standard error and never stops the command.

### The recursion guard

The program that the fallback starts gets `COREAV_FALLBACK_ACTIVE=1` in its environment. A `coreav` started with that variable set never falls back. It refuses with exit status 4 instead, so a wrapper script or a renamed copy of `coreav` on `PATH` cannot cause a loop.

## Decoding through FFmpeg in builds with a decoder backend

Builds with the `ffmpeg-fallback` [build feature](/build-features) also use an `ffmpeg` program to decode video for [`coreav thumbnail`](/commands/thumbnail), [`coreav transcode`](/commands/transcode) and the `libx264` command lines of [`coreav ffmpeg`](/commands/ffmpeg). This is a separate path from the command-line fallback, and it is never in a default build. Strict-safe mode turns it off too ([what strict-safe mode covers](#what-strict-safe-mode-covers)). Outside strict-safe mode:

- CoreAV demuxes the file itself and sends FFmpeg only the packets of one video stream, in a Matroska stream that CoreAV writes. FFmpeg's container probing never runs on the untrusted file.
- The decoder is chosen by name from an allowlist, so a file cannot steer FFmpeg to another decoder.
- FFmpeg runs as a child of a separate worker process with resource limits. Its libraries are never linked into CoreAV.

## Encoding AAC audio through FFmpeg

CoreAV has no AAC encoder of its own. [`coreav transcode --audio aac`](/commands/transcode) and the `-c:a aac` command lines of [`coreav ffmpeg`](/commands/ffmpeg) encode AAC-LC with FFmpeg's built-in `aac` encoder, run as a separate program that you install. Both are in every build with a decoder backend, and strict-safe mode refuses both ([what strict-safe mode covers](#what-strict-safe-mode-covers)). Through `coreav ffmpeg`, only the `-c:a aac` command lines that CoreAV runs natively take this path: those that also encode the video with `-c:v libx264` and select one audio stream that the encode takes (below). Any other `-c:a aac` command line, such as `-c:v copy -c:a aac`, is not native: outside strict-safe mode the [fallback](#the-ffmpeg-fallback) hands it to the real `ffmpeg`, which reads the file itself, and nothing below applies to it. Outside strict-safe mode, on the native path:

- **The program.** CoreAV runs the `ffmpeg` program that `--ffmpeg` names (`coreav transcode` only), else the file that `COREAV_FFMPEG` names, else the first `ffmpeg` on `PATH`. If `COREAV_FFMPEG` names something that is not a file, CoreAV does not look on `PATH`. The program must have FFmpeg's built-in `aac` encoder.
- **When it is missing.** Before any audio is decoded, CoreAV asks the program with `-h encoder=aac`. If no program is found, or its answer does not describe the `aac` encoder, `coreav transcode` stops with exit status 1 and a `coreav.error/1` object of kind `unsupported_feature`, whose message begins `no ffmpeg program for AAC audio` or says that the program `has no aac encoder`. No output is written. For `coreav ffmpeg` these are refusals like any other: the [fallback](#the-ffmpeg-fallback) runs the command line with the real `ffmpeg` when it finds one, and otherwise the refusal stands, with exit status 4.
- **What FFmpeg sees.** CoreAV decodes the audio itself and sends the encoder only 32-bit float samples on its standard input, never the file. On Linux the encoder runs with resource limits: no file writes and an address space of 2 GiB. On macOS the address space is not limited (the budget is advisory, as above), and on Windows neither limit applies. On every system the encoder is killed at the deadline, and CoreAV reads its output back with its own Matroska parser and checks it before it uses any of it.
- **Which inputs.** The audio encodes, `--audio aac` and `--audio opus`, take FLAC or MP3 only, in every build, although CoreAV also decodes Opus and, in a build with the `aac` feature, AAC. The encode takes the first FLAC or MP3 audio stream and passes over AAC and Opus streams before it; a source without one is refused. The stream must be mono or stereo. For AAC its sample rate must be one of the AAC rates from 8 to 64 kHz (8, 11.025, 12, 16, 22.05, 24, 32, 44.1, 48 or 64 kHz), because CoreAV does not resample it: a 22 kHz or 96 kHz stream is refused.
- **Known limit.** When an MP4 source's audio track starts with an empty edit (its sound starts after time 0), CoreAV's decoder writes that edit as silence, and the encoder encodes the silence. The output's audio track starts at time 0 with that silence instead of an empty edit. The sound stays in sync with the video. A Matroska audio stream that starts after time 0 keeps its start as an empty edit.
