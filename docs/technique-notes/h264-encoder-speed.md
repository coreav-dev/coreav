# H.264 encoder search efficiency

This note compares two encoders with CoreAV's independently committed [pre-study search-efficiency design](https://github.com/coreav-dev/coreav/blob/3a5b29fd108f229de85128a6cf4cdcf16b1bd9b2/docs/design/h264-encoder-p.md#pre-study-search-efficiency-design). It answers that design's five questions. It does not prescribe an implementation or report an optimization result.

The motivating CoreAV profile places most work in partition search. Prediction, cheap motion scoring, finalist rate-distortion optimization, reference sampling, and cache preparation overlap within that work. This study makes no per-technique timing measurements. The speed explanations below identify work avoided, not measured speedups or an attribution of the total gap to x264. A comparison of complete encoders cannot isolate any one technique.

## Sources and specification boundary

The [x264 source](https://code.videolan.org/videolan/x264/-/tree/0480cb05fa188d37ae87e8f4fd8f1aea3711f7ee) is core 165 at commit `0480cb05fa188d37ae87e8f4fd8f1aea3711f7ee`, the revision pinned by CoreAV's `scripts/oracle-ffmpeg.env`. x264 has no release tags, so this study uses that exact revision rather than a moving branch. The studied files are GPL-2.0-or-later, as their headers state. The repository also offers commercial licensing. References to x264 below always mean this pin and the GPL-licensed source, not a commercial edition.

The second source is [Cisco OpenH264 release `v2.7.0`](https://github.com/cisco/openh264/tree/1bca62311e447fd9c39fc93de2c4b96cd5ce971c), commit `1bca62311e447fd9c39fc93de2c4b96cd5ce971c`, under its BSD-2-Clause license. References to OpenH264 below always mean that release. Both repositories were cloned outside CoreAV for this study. No source, tables, tuning constants, or implementation comments are included here.

Rec. ITU-T H.264, version 15, August 2024, remains the authority. Clause 8.4 defines inter prediction, clause 8.5 defines inverse scaling and reconstruction, and clause 9.2 defines CAVLC. Clause 7 defines syntax and semantics, and Annex A constrains the admitted streams. Encoder search order, candidate pruning, forward quantization policy, and rate-distortion objectives are not normative decoder processes. Faster search may change the selected stream without changing those requirements.

CoreAV's committed design keeps fixed QP, one reference, the existing coding tools, safe scalar Rust, bounded fallible storage, and transactional failure. It separates heuristic search changes from exact arithmetic and reuse changes. This note keeps that separation. Neither agreement between two encoders nor a plausible reduction in work is evidence that a technique beats CoreAV's own design.

## Partition pruning and early skip

The useful technique is to spend search work according to evidence that a region needs it. A whole-macroblock prediction can explain uniform motion without searching every smaller partition. Cheap prediction costs can indicate whether a split merits expensive evaluation. A skip candidate can avoid residual and partition work altogether. The saved work includes motion probes, interpolation, transforms, and syntax trials, so reducing the number of searched layouts can matter more than reducing the cost of one probe.

This serves motion derivation and prediction in clause 8.4.1 and the macroblock syntax in clause 7. P_Skip must use its specified derived vector and have no residual. Small prediction error is evidence for an encoder decision, not permission to substitute an arbitrary searched vector for skip. Annex A's motion-count and macroblock-bit limits still apply before a candidate can win.

In x264, `encoder/analyse.c`, especially `x264_macroblock_analyse`, `mb_analyse_inter_p16x16`, and `mb_analyse_inter_p16x8`, uses prediction costs and analysis settings to avoid some partition work. Its skip probe in `encoder/macroblock.c`, `macroblock_probe_skip_internal`, considers transformed and quantized residual significance. That is more permissive than requiring identical source and predicted pixels. OpenH264's `codec/encoder/core/src/svc_base_layer_md.cpp`, especially `WelsMdInterFinePartition`, `WelsMdInterMb`, and `WelsMdPSkipEnc`, also uses inexpensive costs and neighbouring skip information to limit work. Its skip decision can use prediction error or residual tests. Neither implementation establishes that the omitted alternatives could not have won complete RDO.

Spatial coherence and the cost of testing extra partitions follow from the compression problem. The particular cost thresholds, neighbour gates, and coupling to selectable analysis levels do not. The studied code supports configurable quality and speed policies through mutable C or C++ analysis state. Those choices are useful evidence of a tradeoff, not a reason to reproduce their decision order. A design without that coupling can make the admissible candidate set and the heuristic search policy separate concepts.

CoreAV already proposes that separation. Its initial early-skip experiment requires zero distortion in Y, Cb, and Cr, and its split ranking retains a whole layout and an intra fallback. This is deliberately narrower than the studied skip tests. Even zero distortion is not a proof that skip minimizes the complete rate-distortion objective, including syntax effects. The study supports testing evidence-based pruning, but supplies no reason to replace CoreAV's proposed policy with either encoder's gates. Compare motion-boundary and chroma behavior, bitrate, quality, and actual searched layouts against the bounded-search reference before broadening it.

## Reference access and interpolation reuse

Repeated motion probes often read overlapping reference samples. Edge extension prepared once removes repeated coordinate clipping from those reads. Reusable half-sample results amortize the more expensive interpolation across probes, while quarter-sample predictions can combine the needed samples. These are distinct savings. Preparing every fractional sample also costs memory traffic, even when search never uses it.

The required values come from clause 8.4.2.2.1 for luma and clause 8.4.2.2.2 for chroma. Padding is a representation of the specified edge extension, not a new boundary rule. Diagonal luma interpolation needs the specified intermediate precision. Clipping an intermediate as though it were already a reconstructed sample can change later results. Chroma has a separate interpolation process and cannot share luma's phase interpretation.

x264's `common/frame.c`, in `plane_expand_border`, `x264_frame_expand_border`, and `x264_frame_expand_border_filtered`, prepares extended reference storage. Its `common/mc.c`, in `x264_frame_filter`, `hpel_filter`, and `get_ref`, maintains reusable picture-scale half-sample planes and can expose an existing reference region without copying it. OpenH264's `codec/common/src/expand_pic.cpp`, in `ExpandReferencingPicture` and its expansion routines, also prepares picture borders. In contrast to x264's persistent filtered planes, the studied fractional refinement in `codec/encoder/core/src/md.cpp`, `MeRefineFracPixel`, uses local half-sample and quarter-sample scratch. Its `codec/common/src/mc.cpp`, `McLuma_c`, provides phase-specific interpolation. The two sources demonstrate different reuse scopes, not a universal winner.

Overlap and interpolation arithmetic are properties of the problem. Aligned raw pointers, fixed scratch strides, and architecture-specific function dispatch reflect the studied implementations' C and C++ kernel interfaces. Picture-scale filtering also fits workloads with many probes and repeated reference use. Those workload assumptions need not hold for CoreAV's single-reference bounded search. A design free of those interfaces can expose validated read-only regions and choose a reuse lifetime without adopting either buffer layout.

CoreAV's committed local-window design is the better starting comparison, not an inferior substitute for full-picture planes. It bounds preparation to the region being searched and computes phases lazily. OpenH264 provides evidence that local fractional scratch is practical. x264 identifies a competing option when reuse becomes dense enough to repay picture-scale preparation. Neither observation proves that CoreAV should add full-picture planes. Count prepared and consumed samples, cache hits, and preparation work alongside full encode time. Reference identity, component, region, and phase must govern reuse, with invalidation on reference replacement and a correct sampled fallback outside the cached region.

## Predictor-driven motion scoring and termination

Motion search can rank many candidates without reconstructing residuals. Prediction error plus an estimate of motion signalling cost is cheaper than complete RDO. Good predictors can reduce the distance that a spatial search must cover. Termination has two different meanings here. A search can stop heuristically because its current answer looks adequate, or an individual score calculation can stop because its accumulated nonnegative terms already exceed the retained-candidate cutoff. Only the latter can be an exact rejection for that same cheap score.

This supports clause 8.4.1's motion prediction and clause 8.4.2's sample prediction. For CoreAV's CAVLC path, clause 9.1's Exp-Golomb process determines the signed motion-difference length. That length is not the entire macroblock rate. SAD, the sum of absolute sample differences, and SATD, a transformed-residual absolute cost, are ranking proxies. Neither is a lower bound on the final reconstruction-distortion-plus-rate objective.

x264's `encoder/me.c`, in `x264_me_search_ref` and `refine_subpel`, evaluates motion predictors, uses motion-cost lookups, and separates inexpensive search metrics from later refinement. Its search methods trade probe count against search coverage. OpenH264's `codec/encoder/core/src/svc_motion_estimate.cpp`, in `WelsMotionEstimateInitialPoint`, `WelsMotionEstimateSearch`, and `WelsDiamondSearch`, similarly combines predictor candidates, SAD, and motion-cost lookup data. It can stop the wider search using predicted cost and can calculate SATD for a selected result. These observations support staged scoring. They do not establish that either implementation uses CoreAV's proposed row-wise exact cutoff.

Predictor coherence and avoiding residual reconstruction follow from the problem. The specific neighbourhood patterns, termination thresholds, and lookup-table representation do not. Both implementations have interfaces that can score several neighbouring candidates through specialized pixel kernels. That favors regular batches of complete scores. A safe scalar implementation can instead exploit partial row sums, while a future vectorized implementation might prefer batches. The tradeoff is between work skipped and work executed efficiently, not between a correct and an incorrect metric.

CoreAV's design already protects zero and the normative predictor, derives signed Exp-Golomb lengths arithmetically, and proposes partial SAD termination only on a strict excess. Retaining equality preserves deterministic ties. Those choices remain independent of the studied search patterns and tables. A small SATD reranking experiment is worth comparing with SAD-only ranking, but must demonstrate that better finalists repay the extra transforms. Keep the existing probe and finalist caps for that comparison. A predicted-cost stop that omits probes would be a separate quality-affecting experiment, not an exact implementation of the row cutoff.

## Incremental finalist evaluation

The reusable unit is work whose inputs and dependencies have not changed, not an entire candidate identified only by its motion vector. Unchanged block predictions, coefficients, and distortion can survive a nearby trial. Their syntax costs may not survive. Motion predictors depend on selected earlier partitions, and CAVLC coefficient coding depends on neighbouring nonzero counts. Chroma DC couples blocks that otherwise appear independent. Reusing numerical results without those dependencies can make a fast evaluator disagree with the emitted stream.

This spans prediction in clause 8.4, inverse reconstruction in clause 8.5, macroblock syntax in clause 7, and CAVLC in clause 9.2. Annex A admission still needs complete candidate information. CABAC state reuse is a different problem under clause 9.3 and is outside CoreAV's committed scope.

x264's `encoder/rdo.c`, in `rd_cost_mb`, `rd_cost_subpart`, and `x264_rd_cost_part`, has both whole-macroblock and region-focused evaluation. It shares syntax-writing logic with cost evaluation. Its CAVLC counting path counts bits without producing output, while its CABAC path uses fractional-bit estimates and temporary context state. Region costs are not evidence that an arbitrary sum of independent block costs equals a complete admitted macroblock cost. OpenH264 supplies a useful contrast rather than a second exact incremental-RDO design. In the studied `codec/encoder/core/src/svc_base_layer_md.cpp` path, `WelsMdInterMbRefinement` retains prediction work in macroblock scratch, and `WelsMdInterEncode` consumes prepared predictions for encoding. This path relies on cheap mode costs rather than establishing full syntax-counted RDO for every trial.

Local pixel work and syntax dependencies follow from H.264. x264's mutable encoder context and macro-based reuse of C writers are implementation choices, as are OpenH264's scratch-buffer interfaces. They need not become CoreAV's ownership model. A design without those constraints can keep trial state private and represent validity by the inputs that produced each retained result. It can also deliberately recompute syntax when a dependency is cheaper to traverse than to cache correctly.

CoreAV's proposal to retain block work but initially keep the complete shared syntax traversal is the conservative exact design. The studied code does not justify skipping that traversal or weakening macroblock admission. Expand reuse only where equality with uncached evaluation includes predictions, levels, reconstruction, costs, and refusal behavior. Coupled chroma DC and dependent motion differences must be recomputed when their inputs change. OpenH264's cheaper decision path is an alternative quality policy, not a replacement for CoreAV's exact finalist contract.

## Specialized transforms and QP-derived arithmetic

Fixed-size separable integer transforms avoid evaluating a general two-dimensional basis independently for every output. QP-derived quantization parameters can move repeated setup out of the coefficient loop. Avoiding general division can reduce arithmetic cost further, but a reciprocal multiply and shift is not automatically equivalent to another quantizer. Signed rounding, ties, overflow, and DC treatment determine the resulting levels.

Clause 8.5 specifies inverse scaling and reconstruction. Forward transform and quantizer choices are encoder decisions subject to producing legal coefficients and the matching reconstruction. Thus preserving CoreAV's current quantizer is an additional exactness contract, not a requirement to match x264 or OpenH264's forward policy. A claim that a residual is zero must include the applicable DC process, particularly coupled chroma DC.

x264's `common/dct.c`, in `sub4x4_dct` and `add4x4_idct`, specializes the small integer transforms. Its `common/set.c`, `x264_cqm_init`, derives quantization and inverse-scale data outside the hot coefficient loop. Its `common/quant.c`, `quant_4x4` and `dequant_4x4`, uses that data for coefficient arithmetic. OpenH264's `codec/encoder/core/src/encode_mb_aux.cpp`, in `WelsDctT4_c`, `WelsQuant4x4_c`, and `WelsQuant4x4Dc_c`, also uses specialized transforms and multiply-and-shift quantization. Its `codec/encoder/core/src/svc_encode_mb.cpp`, `WelsEncInterY`, selects QP-indexed parameters. These are two instances of specialization, not sources for arithmetic constants or quantization tables.

Separability and a fixed QP's repeated scale are mathematical opportunities independent of either codebase. Their narrow coefficient storage, aligned parameter layouts, batch entry points, and CPU dispatch reflect C and C++ interfaces designed to support specialized kernels. Those layouts are not necessary for scalar Rust. Nor does the existence of a tuned quantization bias make that bias appropriate for CoreAV's current quality objective. Independently derived, checked picture-local parameters can retain a simpler lifetime and explicit intermediate widths.

CoreAV's committed row-and-column factorization and picture-QP preparation already address the main opportunity. Preserve that design before considering reciprocal arithmetic or batching. Compare the specialized scalar path with the generic path across every admitted QP, coefficient boundary, sign, tie, DC case, and range refusal. A faster quantizer that changes levels belongs in a separate quality-policy comparison. No isolated arithmetic speed measurement was made in this study, so source specialization alone cannot rank this work above partition pruning or prediction reuse.

## What the comparison permits

The two sources support investigating less repeated work, but do not select an implementation for CoreAV. The committed design remains the comparison arm. Heuristic partition and motion policies need bitrate and quality comparisons as well as time and probe counts. Exact reference, finalist-state, and arithmetic changes additionally need complete agreement with their uncached or generic references, including refusals and rollback.

Only a same-run comparison against CoreAV's design or another independently derived alternative can justify adopting a studied technique. Conformance and complete decoder-reconstruction checks remain unchanged. No source-derived production code is part of this note, and neither this study context nor its independent note reviewer may implement the H.264 encoder. A fresh implementation context may use the specification and this note only after independent review and commitment. Source clones are removed after study, and any later note-derived code still requires the encoder similarity guard.
