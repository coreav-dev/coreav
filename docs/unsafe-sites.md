# `unsafe` sites

Every `unsafe` site in production crates, and every confined test-only `unsafe` site in the workspace, is listed here: where it is, what it does and the precondition that makes it sound. The PR that adds or changes `unsafe` adds or updates its row. Spike code is not listed; their `unsafe` never reaches production code.

`scripts/unsafe_sites_check.py`, run by CI, keeps the table complete. A row's first cell is the path of one file, in backticks: each Rust file that uses `unsafe` (a block, function, impl, trait or extern block, an `unsafe(...)` attribute or one of the attributes that need it, or an `allow`, `expect` or `warn` of `unsafe_code`), and the `Cargo.toml` of each crate that does not take the workspace's `forbid`, get one. The check fails when one is missing, when a row names a file that no longer exists, or when the workspace's own level is not `forbid`. It covers `crates/`, `tools/`, `packages/` and `bench/`, fuzz projects included; spikes are outside it.

Everything else builds under the workspace `unsafe_code = "forbid"`: every other production crate, the bindings (`coreav-py`, `coreav-wasm`) and the tools. The PyO3 crate `coreav-py`, which the `unsafe` policy allows to lower the lint to `deny`, builds under `forbid` (`docs/design/python.md`) and needs no row.

The H.264 decoder's hot-path module (`crates/coreav-h264/src/fast/`) is allowed `unsafe` Rust or `asm!` at named sites. A site has a row naming the site, what it does and the precondition that makes it sound, and the crate's `Cargo.toml` has its lint-table change; the PR that adds a site also carries its A/B against its safe twin, its fuzz target and its differential test. It has two sites today. The `v3-entry` site (`docs/design/h264.md`, "Kernel round: the hot paths compiled twice") covers the calls from the decoder's code into its x86-64-v3 instance of its hot paths (two per-block functions, and `v3::enter`, which runs any other function's body in the instance), each a safe function with `#[target_feature]` that only a `fast::V3` may call, and a `V3` exists only where `V3::detect` found every feature those functions are compiled with. The `v3-entry` site's `unsafe` is the call alone; it forms no pointer and reads nothing. The `decision` site (`docs/design/h264.md`, "Entropy round: DecodeDecision in assembly") implements DecodeDecision with RenormD in one `asm!` block. It reads fixed tables at indices bounded by construction, writes no memory and never reads the slice data; the `V3` passed in proves the CPU has BMI2. A build without the feature `fast` compiles none of it.

There are six exceptions in use today, each with rows in the table: the H.264 kernel crate, the audio kernel crate, the H.264 decoder's hot-path module (above), the libvpx backend, the decode worker's shared memory (`docs/design/decode.md`, "The sandboxed worker") and the test-only counting allocator, in the table's order. The H.264 kernel crate, which the `unsafe` policy allows to use SIMD intrinsics, has the first rows. Its `unsafe` is of three kinds, all confined to the `simd` module:

1. **Loads, stores and block copies.** Most are in a helper at the top of its architecture's file (`load16`, `load8`, `store_bytes`, `load_i16x8`, `store_i16x8`, `load4_i32`, `load8_i32`, an `unsafe fn` since its 256-bit load needs AVX, and `store8_bytes` on arm64), and each checks the length of the slice it was handed immediately before it forms a pointer, falling back to a padded array where the slice is shorter than the vector. The exceptions are the luma interpolation's and the deblocking filter's. The luma interpolation (`x86::luma_mc_into`, which runs `x86::interpolate` for each width and quarter-sample position) checks, before any pointer exists, that the window's `h + 5` rows of `w + 5` samples and the block's `h` rows of `w` end inside their slices (`x86::window_fits`: `(n - 1) * stride + w` in checked arithmetic, an overflow failing the check), and accepts only 8- and 16-wide blocks of 1 to 16 rows, with one exception: a 4-wide block of 1 to 16 rows whose window is 9 wide and 5 rows taller goes to `x86::luma4_padded`, which copies the window, in safe Rust, into a local array of 21 rows of 16 bytes and the block into one of 16 rows of 8, runs the 8-wide kernel (`luma_mc_ptrs`) on pointers to those two arrays (rows 16 and 8 apart), and copies 4 bytes of each of its rows back into the block; the arrays' sizes, against at most 21 rows of 13 bytes read and 16 rows of 8 written for `h` at most 16, are its precondition, and its output columns 0 to 3 read only window columns 0 to 8. It then reads source rows 0 to `h + 4` and writes block rows 0 to `h - 1` through pointers, each read or write of `w` bytes from a column that keeps it inside its row (2 or 3 for a full sample and the vertical filter), except the horizontal filter's (`Row::b1`), which reads the `w + 5` samples of a row as two loads that end inside it (bytes 0 to 15 and 5 to 20 of a 16-wide block's row, 0 to 7 and 5 to 12 of an 8-wide one's); a weighted block at a full-sample position (`x86::weigh_full`) reads the window's rows 2 to `h + 1` from column 2 and reads and writes the block's rows, `w` bytes each; the pointers step from row to row with `wrapping_add`, so the steps past the last row form no pointer that is read or written. Where a check fails, no pointer is formed and the block goes to the reference. The deblocking filter's `x86::gather` and `x86::scatter` follow the same argument for the lines of an edge of the standard length (sixteen luma lines, eight chroma lines): one check that `n` rows of `w` bytes, the first at `start` and each `stride` further, end inside the slice (`(n - 1) * stride + start + w`, checked arithmetic, an overflow failing the check), then one unaligned read or write of `w` bytes per row between a byte array and the slice; where the check fails, no pointer is formed and each row goes through the slice, a row past its end reading as zeros and not written. The standard edges (sixteen luma or eight chroma lines) other than horizontal luma edges read and write their rows through `x86::rows_at` and `x86::rows_at_mut` instead: the same check (`rows_fit`) before the pointer to the first row is returned, then one unaligned load or store of at most `w` bytes from the start of each row `k < n` (`movq` loads and stores, an unaligned 64-bit write of a transposed pair's high half, a 32-bit load and a 16-bit store per line of a vertical chroma edge; none is a typed access that needs alignment); where the check fails, they return `None` and the edge goes through `gather` and `scatter`. The inverse transforms (`x86::idct4x4_add_quad`, `x86::idct8x8_add`) and the chroma residual of a macroblock (`x86::chroma_residual_mb`, for each plane's block) make the same check through `rows_at_mut` for the eight rows of eight samples of their block and then, in `x86::add_four_rows`, `x86::load_four_rows` and `x86::store_four_rows`, read and write rows 0 to 7 through the pointer: per two rows a `movq` load, an unaligned 64-bit read, a `movq` store and an unaligned 64-bit write, none a typed access that needs alignment; where the check fails, the block goes to the reference. The paired chroma filter (`x86::filter_chroma_pair`, `x86::chroma_pair`) makes the same check through `rows_at_mut` for each plane's edge, four rows of eight samples (p1 to q1) of a horizontal edge or eight rows of four of a vertical one, before it reads anything; it then reads those rows and writes p0 and q0 back inside them through the two pointers (`movq` loads and stores, unaligned 32-bit reads and 16-bit writes, none a typed access that needs alignment), and where either check fails both edges go to `x86::filter_edge`. The chroma edges of a macroblock in one call (`x86::chroma_mb::filter_chroma_mb`, with `vertical_edges`, `horizontal_edges`, `both` and `store_both`) make the same check through `rows_at_mut` for each plane's window, the ten rows of ten samples that `ChromaMbMut::new` (a view of `views.rs`, which checks its range in checked arithmetic and requires a stride of at least ten, so that the rows do not overlap) hands out, before they read anything, and require a stride of at least ten themselves; the check gives bytes 0 to `9 * stride + 9` from the window's first. They then read sixteen bytes of window rows 2 to 9 from column −8 (bytes `2 * stride - 8` to `9 * stride + 7`; the bytes before a row's first are the end of the row above) and write eight bytes of each from column 0 (the vertical edges), and read sixteen bytes of window rows 0 to 7 from column 2 (bytes 2 to `7 * stride + 17`, which is below `9 * stride + 10` for any stride of at least four) and write eight bytes of rows 1, 2, 5 and 6 from column 2 (the horizontal edges): unaligned 128-bit loads (`vmovdqu`, `vinserti128` from memory) and 64-bit stores (`movq`, `movlpd`, `movhpd`), none a typed access that needs alignment; where either check fails, the planes' strides differ, or a t'C0 the parameters select is above 31, the edges go to `x86::filter_chroma_pair` one at a time. Its parameters (`lanes`) are read as bytes from the call's `&[[EdgeParams; 2]; 4]`: `EdgeParams` is `repr(C)` with fourteen `u8` fields and no padding (a compile-time assertion of its size and alignment in `lib.rs`), so each pass's `&[[EdgeParams; 2]; 2]` is 56 initialised bytes, and `lanes` reads bytes 0 to 15, 12 to 27, 28 to 43 and 40 to 55 of it (unaligned 128-bit loads); the type fixes that extent, and no check is made at run time. The intra kernels (`x86::intra16x16`, `x86::intra_chroma`, `x86::intra4x4_mb`, `x86::intra8x8_mb`, and `x86::intra_chroma_mb` for each of its two views) check, through `x86::IntraRows::of`, that the view is the block size the kernel predicts, that its `n` rows of `n` samples end inside the view's slice (`rows_fit`), and that the block's first sample lies at least as far into the slice as each neighbour the view's flags name requires (`stride + 1` for the sample above and left, `stride` for the row above, 1 for the column left). They then read and write through pointers into the slice formed by `IntraRows::at` with wrapping arithmetic: the block's rows (16- or 8-byte stores, 4-byte stores of each Intra_4x4 block's rows, and 8-byte stores of each Intra_8x8 block's and of each chroma block's in `intra_chroma_mb`, `movq` and unaligned 64-bit writes), the row above (16 or 8 bytes, 8 bytes from an Intra_4x4 block's column, which ends at most 20 samples along, and 16 bytes from an Intra_8x8 block's column, which ends at most 24 samples along, in the row above the macroblock or its eighth row, both before the macroblock's last row ends since its stride is at least 16), the column left and the sample above and left, each read only where the view's flags (or, inside an Intra_4x4 or Intra_8x8 macroblock, the block's availability, which names a neighbour outside the macroblock only where the view's flags do) say it exists, except a block's samples above and right (four of an Intra_4x4 block, eight of an Intra_8x8 one), which are read with the row above and replaced where the block has no top right; they lie inside the view whenever the row above does. Where the check fails, the block goes to the reference. The AVX-512 tier's luma edges of the standard length (`avx512::luma_rows`, `avx512::luma_columns`) make the same check through `rows_at_mut` for the whole edge, the eight rows of sixteen samples p3 to q3 of a horizontal edge or the sixteen rows of eight of a vertical one, before they read anything; they then read those rows and write rows 1 to 6 of a horizontal edge, or every row of a vertical one, back inside them through the pointer (16-byte unaligned loads and stores; unaligned 64-bit reads, `movq` stores and unaligned 64-bit `f64` writes of a register's high half; none a typed access that needs alignment), and where the check fails the edge goes to `x86::filter_edge`. The AVX-512 tier's boundary strengths (`avx512::strengths`) read the motion of a macroblock's sixteen blocks from a `&[Motion; 16]`, whose type fixes its extent: `Motion` is `repr(C)`, twelve bytes without padding (a compile-time assertion beside it), so the array is 192 initialised bytes. `load` makes six unaligned 32-byte reads at bytes 0 to 160, `column3` four unaligned 16-byte reads at bytes 32, 80, 128 and 176, and `row3` an unaligned 32-byte read at byte 144 and a 16-byte one at byte 176; every read ends at or before byte 192, and none is a typed access that needs alignment. Its one write (`assemble`) is an unaligned 32-byte store into a local `[[u32; 4]; 2]`, which is 32 bytes. Those reads and that write rest on the types alone, with no check at run time. The other sites in this paragraph are the only places in the crate where a pointer is formed after the check that justified it rather than immediately before. The kernels otherwise work on the slices the views of `views.rs` hand out, and a view's constructor has already checked every length, stride and range with checked arithmetic. The one view made without a check of its own is an edge of a luma window (`LumaMbMut::vertical`, `LumaMbMut::horizontal`): it holds the whole window, which `LumaMbMut::new` checked, and its offset; no kernel relies on an edge's slice being exactly its samples, since each of the checks above is made against the slice the edge holds, so such an edge is no less safe than one `EdgeMut::new` made.
2. **Calls into `#[target_feature]` functions** (x86-64 only). They are safe to call exactly where the CPU has AVX2, which only `Simd::detect` establishes; holding a `Simd` is the proof, and `Simd` has no other constructor. The AVX-512 tier's functions (`simd/avx512.rs`) also need AVX-512 F, BW, VL and VBMI, which `Simd::detect` checks too: it sets the `Simd`'s `avx512` flag only where the CPU has them, `Simd::without_avx512` only clears it, and the dispatch calls the tier only where the flag is set. On arm64 NEON is part of the baseline, and the functions are `unsafe fn` only because the intrinsics are. The x86 chroma interpolation (`x86::chroma_mc`) is the same case as arm64: it uses SSE2 alone, which every x86-64 CPU has, so it is an ordinary function, and its `unsafe` blocks wrap register intrinsics only. It reads and writes samples as fixed-size arrays of the views' slices (`first_chunk`, `from_le_bytes`) and forms no pointer. The luma interpolation's helpers (`x86::Row` and its two implementations, `tap6`, `horizontal`, `five`, `sample`, `interpolate`) use AVX2 intrinsics without `#[target_feature]`: they are `#[inline(always)]` `unsafe fn`s whose contract is that AVX2 is available, called only from `x86::luma_mc_into`, which has the attribute, so that they and their intrinsics inline there (a helper with the attribute was left out of line, a call per row).

3. **Prefetch hints** (x86-64 only): `simd::hint_read`, behind the safe `prefetch::rows_for_read` and `prefetch::rows_for_write`, issues one `prefetcht0` for the address it is handed, which `prefetch::for_rows` computes from the plane's slice: from the first row's address and the stride once it has checked that the last row's index lies inside the slice (16, 8, 4 and 2 rows), or else a subslice from a checked start, walked a stride at a time. A prefetch makes no architectural access, cannot fault and changes no value; SSE, which has it, is part of the x86-64 baseline. Elsewhere the hints are no-ops. Ownership hints: `simd::hint_own`, behind the safe `prefetch::Ownership::rows`, issues one `prefetchw` (written as `asm!`, its target feature `prfchw` being unstable) for an address that `prefetch::for_rows` computes as above; an `Ownership` exists only where `simd::has_prefetchw` found the instruction (CPUID leaf 0x8000_0001, ECX bit 8, read only where leaf 0x8000_0000 says it exists; CPUID is in the x86-64 baseline).

The arithmetic between a load and a store is intrinsics over registers: no pointers, no indexing, no allocation.

The audio kernel crate (`crates/coreav-kernels-audio`, `docs/design/audio-decode.md`, "Resampling and downmixing"), a SIMD kernel crate as the `unsafe` policy allows, has one file of `unsafe`, `src/avx.rs`, the x86-64 filter loop of the resampler. Its `unsafe` is of two kinds. **The call** into the `#[target_feature(enable = "avx")]` function `run`: an `Avx` value is the proof that the CPU has AVX, and only `Avx::detect` makes one, from `is_x86_feature_detected!("avx")`. **The loads**: `lanes` (one window) and `lanes4` (four windows in one loop) read `taps` floats from each of two pointers per window, eight at a time (`_mm256_loadu_ps`, unaligned, at offsets `j` with `j + 8 <= taps`); the pointers are `input.as_ptr().add(start)` and `table.as_ptr().add(row)` for a window `(start, row)` of a `Checked` (`src/checked.rs`, safe Rust), which `Avx::run` takes and which only `Checked::new` makes, its fields private to its module, after checking `taps` a positive multiple of 8, the outputs as many as the windows (`Fir::run` passes `out.len()`; `out` is written through slices, so its length is not a safety condition), and for every window `start + taps <= input.len()` and `row + taps <= table.len()` in checked arithmetic (an overflow refuses); `Fir::run`, the crate's only entry point, makes it before any kernel runs. Where the check fails nothing is computed. Outputs are written through slices, not pointers. A differential test and the fuzz target `fir` compare the kernel with the portable one bit for bit. **The FFT kernels** of `coreav-opus`'s inverse MDCT (`Fft::pass`, `Fft::rotate`): the calls of the `#[target_feature(enable = "avx")]` functions `fft_pass` and `fft_rotate` from `Avx::pass` and `Avx::rotate`, under the same proof; inside them, `Oct`'s intrinsics, which are arithmetic on registers except for the loads and stores of `Oct::load` and `Oct::store`, each reading or writing the eight floats of a `&[f32; 8]` or `&mut [f32; 8]` that `first_chunk` returned, so no pointer leaves a checked slice. `Oct` is private to the module and made only inside those two functions. A unit test compares every pass shape and the rotation with the portable kernels bit for bit. Off x86-64 the crate forbids `unsafe`.

The dav1d backend (`crates/coreav-backend-dav1d`, `docs/design/decode.md`, "dav1d") is a decoder-backend crate, which the `unsafe` policy allows `unsafe`, but it has none of its own and builds under the workspace's `forbid`, so it has no row. It reaches libdav1d (C, BSD-2) through the `dav1d` and `dav1d-sys` crates of the rust-av project (MIT, accepted by `deny.toml`), whose `unsafe` is a dependency's, outside this list like every other dependency's. Only builds with its `dav1d` feature link libdav1d, and `coreav thumbnail` runs it inside the sandboxed worker.

The libvpx backend (`crates/coreav-backend-libvpx`, `docs/design/decode.md`, "libvpx") is a decoder-backend crate under the same exception, with CoreAV-authored FFI: no maintained binding of libvpx's decoder fits the licence policy and the build (the reasons are in the design note). Its `unsafe` is in `src/ffi.rs` alone: declarations of eleven functions of libvpx's decoder API and of the three structures they share, from libvpx's public headers, and the calls through them behind a safe API (one decoder instance, and each decoded image lent as rows checked against its own geometry). Packets reach libvpx only after `src/header.rs` (safe Rust, fuzzed by `crates/coreav-backend-libvpx/fuzz`) has read every frame size they state and the decoder has checked those sizes against the decode limits. Only builds with its `libvpx` feature compile `src/ffi.rs` and link libvpx, and `coreav thumbnail` and `coreav transcode` run it inside the sandboxed worker.

The test-only counting allocator is the one the `unsafe` and limits policies call for; it measures the pinned memory bounds of `docs/design/limits.md`. Its `unsafe` is one `GlobalAlloc` implementation whose four methods forward their caller's pointer, layout and new size unchanged to `std::alloc::System` and return `System`'s pointer unchanged; nothing dereferences a pointer, and the counting that follows touches one `Cell` of plain integers and, for a process-wide region, atomic integers in a module of its own without `unsafe` (`src/process.rs`). Three crates name the allocator, all in their `[dev-dependencies]`, so it is compiled into test binaries and into no library, binary or wheel. Its manifest declares that (`[package.metadata.coreav] test-only = true`) and `scripts/unsafe_sites_check.py` fails if any crate it scans depends on it outside its `[dev-dependencies]`, resolving a rename through `package = "..."` or `[workspace.dependencies]` first.
