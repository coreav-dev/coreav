# Stage 3 correctness report and hostile-file demo

Design note for `tools/stage3-report/`: one command that
regenerates, on a given commit, the report that the correctness and
performance criteria hold for stage 3 and launch 1, and a short demo of a
hostile file that CoreAV rejects while default FFmpeg hands it to a decoder.

## The command

    python3 -I tools/stage3-report/run.py --work DIR [--steps ...] [--workers N]

It builds what it runs (the `coreav` binary, the oracle tools and adapters), generates the fixtures, runs every step, and
writes `docs/measurements/stage3-correctness.md` with its machine-readable
twin `docs/measurements/stage3-correctness.json`. The report names the
commit and whether the tree was clean; a release report is made from a clean
tree. Steps can be run alone (`--steps fixtures,hostile`); the report keeps
the results of the steps not rerun and says which run each came from.

Requirements: the pinned `ffmpeg`, `ffprobe` and MediaInfo
(`scripts/install-oracle-ffmpeg.sh`, `scripts/install-oracle-mediainfo.sh`)
on `PATH`; the R2 credentials of corpus v1 (`R2_ACCESS_KEY_ID`,
`R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT`) for the corpus steps.

## What it measures, and the bars

The bars were fixed before this tool existed.

1. **Fixtures** (generated by `scripts/gen-fixtures.sh` and
   `scripts/gen-fixtures-mkv.sh` with the pinned ffmpeg, never committed):
   the stream and packet oracles against `ffprobe` for MP4/MOV and for
   Matroska/WebM, with the known divergences applied; `--ffprobe-compat`
   output against `ffprobe`; and the fixture checks of every stream-copy
   primitive that CI runs (extraction, clip, remux, sanitize, split, text,
   policy, Matroska remux, HLS packaging), each run as `ci.yml`'s
   `isobmff-fixtures` and `mkv-fixtures` jobs run it: the HLS check takes the
   list of inputs the packager is expected to refuse from `ci.yml` itself, so the two
   cannot drift apart. Bar: **100%** of each (for HLS, of the inputs it
   packages).
2. **Real-file corpus**, probe, every `set: real` file of corpus v1, the
   development and held-out splits reported apart and together:
   MP4/MOV/M4A/3GP (1,049 files) and Matroska/WebM (209 files). Each file is
   downloaded (SHA-256 checked), captured by `ffprobe` and by the adapter
   (streams and packets), compared by `coreav-oracle compare` and overlaid
   with the known divergences (`scripts/oracle_kd.py`,
   `scripts/oracle_kd_mkv.py`), then deleted. Bars: at least **98% of
   files** (stream oracle: agreeing files ÷ (files − ffprobe failures)) and
   at least **99% of packets**, per family, over all real files; reported
   as direct agreement, agreement through known divergences (by entry) and
   uncovered disagreement.

   The same pass runs the `--ffprobe-compat` check on each file
   (`scripts/compat_check.py`, an earlier change): every key the
   command prints is compared with `ffprobe -show_format -show_streams` as
   the string `ffprobe` prints, and a known divergence counts only where
   that file's own overlay checked its predicate. Bar: **every key equal on
   at least 98% of the files that print it**, per family, reported with
   every entry and directly alone. A file whose compat check failed (a
   crash, a timeout: the captures' bound applies) or did not run counts
   against every key. Files CoreAV rejects while `ffprobe` reads them, with
   no known divergence to excuse it, are counted beside the bar rather than
   in it: they print no key, and the streams bar above already counts them
   as disagreeing (the fixture check fails on any such file, where the bar
   is 100%). Every extension is in scope on the corpus, not only MP4, MOV
   and M4A. The record names the `coreav` binary it ran, so a change to the
   command makes it stale (`--recheck stale`).
3. **Second oracle**: the three-way MediaInfo report on the
   fixtures and on the same corpus files, aggregate counts only. Informational: it classifies each CoreAV–ffprobe disagreement by
   MediaInfo's reading; no bar.
4. **Hostile-input suite** (`tools/hostile/generate.py`):
   structural attacks, seeded mutations, the PixelSmash class, Matroska
   block lacing and content compression and the CVE route files
   below, through the native `coreav` binary
   (`scripts/cli_hostile_check.py`, both output modes; Matroska and WebM
   files also through `probe --scan-frame-sizes`, `check` and `remux`,
   which walk their blocks). Bars:
   every case **rejected or bounded as its manifest says, with no crash,
   signal, timeout or out-of-memory**.

### Packet unit

The packets bar counts packets in `ffprobe`'s (the reference's) packet
unit. Both sides list packets one for one, except constant-size linear PCM
in MP4/MOV: CoreAV reports one packet per sample, `ffprobe`
groups consecutive samples into packets of about a thousand (KD-PCM). The
comparison (`coreav-oracle compare`) pairs and counts in the candidate's
unit, so there each sample is one item: a minute of 48 kHz stereo PCM
weighs 2.9 million items against about 2,800 `ffprobe` packets, and in the
corpus KD-PCM alone covered 129.6 of 226.8 million packet items when this
method was set. The bar then measured PCM tiling more than
anything else, and one mistiled PCM stream outweighed every other stream of
the corpus together.

`scripts/oracle_kd.py` (`pcm_reference_units`) therefore recounts each
constant-size PCM stream, which the candidate lists as runs
(`tools/oracle/SPEC.md`, "Runs"):

- each reference packet is one unit: direct when one candidate sample equals
  it (`ffprobe` also lists one sample per packet); covered by KD-PCM when the
  candidate's samples tile it exactly (positions, sizes, timestamps anchored
  at the packet, keyframe flags, and durations that sum to its duration);
  otherwise a mismatch. A mistiled packet stays a mismatch, so a PCM
  packet-size defect still shows;
- each stretch of consecutive candidate samples that starts in no reference
  packet is one unit: KD-EDIT-DISCARD when all of it lies outside the edit,
  else a mismatch;
- when the candidate's packets cannot be laid out by position (one has no
  position, or two overlap), every reference packet of the stream and one
  unit for the candidate's packets are mismatches.

Every other stream counts as the comparison does: one unit per paired
packet and one per unpaired packet on either side. When the overlay cannot
attribute a file's differences to streams, every unit of the file that does
not agree directly stays uncovered, as before. Matroska stores PCM in
blocks that both sides list as packets, so its two counts are equal.

The count in the comparison's unit, one packet per PCM sample, stays in the
overlay output (`per_sample`) and in the report, labelled, and is not a bar.
There KD-PCM covers a stream only when every reference packet of it is
tiled, as before this method, so it stays comparable with earlier runs.

Rejected: keeping the candidate's unit for the bar (the PCM weight above);
counting PCM per stream or per file (a stream with one bad packet would
weigh as much as a stream that is wrong throughout, and other streams
count per packet); pairing in the reference unit inside the comparator (it
would have to know PCM grouping, which is a known divergence and belongs to
the overlay, and it would change the frozen comparison for every file).

### Known divergences and the bars

A known divergence counts as agreement, so an entry written
after the bars were fixed moves the goalposts unless the report says so.
The bars were fixed before any entry existed:
no entry is from before them. `tools/stage3-report/report.py` therefore
holds `PRE_BAR`, empty; `ADDED_AFTER_THE_BARS`, every entry of the probe
overlays (MP4/MOV and Matroska) with the squash commit of the merged pull
request that added it, those that later changed its predicate or coverage,
and a fingerprint (its JSON record and its predicate's source); and
`RETIRED`, entries no longer in the overlays. The dates come from the
merged pull requests: the one that added the entry's id to its JSON twin,
and the ones whose change to the overlay or its documents changed the
entry's fingerprint — what it covers, and the words of its record, which
are part of the fingerprint too. Until the squash commit of such a pull
request exists its record names the commit the change was written on, and
the next pull request that touches `report.py` replaces that with the
squash commit.

The report gives every corpus number twice, side by side: with every entry,
and with the pre-bar entries only (with `PRE_BAR` empty, direct agreement).
The status column judges the bar with every entry, as the oracle policy
counts agreement; the second number shows how much of it the entries carry. An
entry missing from both lists counts as added after the bars, and a test
(`tools/oracle/tests/test_kd.py`, `DatedAgainstTheBars`, run by CI) fails
when an entry of either overlay is in neither list, or when an entry's
JSON record or predicate source no longer matches its fingerprint: a new or
changed entry is dated in the pull request that adds or changes it. (A
change in a helper the predicate calls is not in the fingerprint.)

Scope: the probe overlays, whose numbers are the corpus bars. The other
checks' known divergences (clip, extraction, remux, split, HLS, text,
policy) apply to the fixtures, where the bar is 100% of generated files
built to exercise them, not a real corpus whose results were seen first.

Cost of an empty `PRE_BAR`: the second number no longer separates entries
written before the corpus was first measured from those written after
it; it is direct agreement. Rejected: the first corpus run as the
boundary (the earlier list of three entries), because entries written
earlier were also written while their effect on fixtures and samples could
be seen, and the bars are older than all of them.

Uncovered disagreements are grouped by cause (`causes.py`): per cause, the
files that show it, the files it alone keeps from agreeing, and the packets
it accounts for, so fixes can be ordered by impact. `runs.jsonl` beside the records logs
which commit, adapter and overlay produced each run, and with which
recheck mode.

## Rechecks

Between full runs, a fix is checked by making some records again on top of
a baseline's records (`corpus.py run --recheck MODE`, with a copy of the
baseline's family directory as `--out`). Each record names the tools that
made it (`corpus.py`'s `tools`): the SHA-256 of the adapter, the `coreav`
command (for the compat check), the comparator and the overlay; one SHA-256
over the other local files that shape a record (the capture scripts,
`corpus.py`, the MediaInfo capture, the compat check, the documented
divergence ids and the modules the overlay imports); and the version and
binary SHA-256 of `ffprobe` and MediaInfo. A run without either tool on
`PATH` is refused. The stream captures kept beside it name every stream's codec and
kind on both sides. The modes use those.

| Mode | Makes again | Use it for |
|---|---|---|
| `stale` | every file whose record other tools made, and failed and missing ones | **the totals of a fix**. After any change to what makes a record (the crates behind the adapter, `--ffprobe-compat`, the comparator, an overlay or its imports, the capture scripts, `corpus.py`, `ffprobe` or MediaInfo), that is every file: a full corpus step, some 20 minutes for both families on the development machine. Records made before the fingerprint named all of these count as made by other tools. |
| `affected --codec C,... --kind K,...` | the failed and uncovered files, and every file with a stream of those codecs (`codec_name` or `codec_fourcc`) or kinds | iterating on a fix confined to some streams. Its totals are provisional: a file whose streams the selection does not name keeps its old record, and format-level fields (the format duration) are not selectable. A selector that matches no stream is refused, so a misspelt codec does not turn it into `uncovered`. |
| `uncovered` | the failed and uncovered files | a first look only. |
| `errors`, `all` | the failed files; every file | a failed download or capture; a new corpus, or a change the fingerprint does not see (the Python interpreter, the shell tools the capture scripts run). |

The hole these modes close: a recheck of only the uncovered files cannot
see a file that agreed and that the change makes disagree. For example, a
change to how text tracks report their size can break a file whose chapter
text track `ffprobe` reads as `bin_data`, without a size; the file agreed
before, so `uncovered` does not select it, while `stale` and
`affected --codec mov_text` (or `--kind subtitle`) do: both sides' streams
are matched, and CoreAV reads that track as `mov_text`.
`tools/oracle/tests/test_recheck.py` plants such a regression and requires
`stale` and `affected` to show it and `uncovered` not to.

Choices and rejected alternatives:

- **Totals from `stale`, which is a full run after a code change.**
  Deciding which files a change can affect from its diff would need a map
  from code to codecs that nothing keeps current; a missed file costs a
  regression found at the gate, and a full corpus step costs about 20
  minutes.
- **`affected` names streams, not paths.** The person changing a codec's
  mapping knows which codecs and kinds it touches; the selection then
  takes every file that has one, whether its record agreed or not.
- **`uncovered` kept**, documented as a first look: it is the fastest
  answer to "does the fix help the files it targets".

Not in this report: the 24 CPU-hour fuzz campaign (a separate, longer run)
and speed (each primitive's own measurement).

## CVE route files

For FFmpeg CVEs whose public description (NVD) names the affected component,
the suite holds a small valid file that default FFmpeg routes to that
component by content, whatever the file is called: a PPM image
(CVE-2024-7055, PNM decoder), OpenEXR images alone and in Matroska
(CVE-2020-35965, EXR decoder), an AVI file (CVE-2024-36618, AVI demuxer)
and an SBaGen script (CVE-2024-35366, SBG demuxer), beside the MagicYUV files
of the PixelSmash class (CVE-2026-8461). The generator fails when one of them
cannot be made, so the suite never shrinks silently. They carry no crafted overflow; they show the attack
surface. The pinned FFmpeg 7.0.2 has the fixes for these CVEs, so the point
is that it still reaches the component, where the next bug lives, while
CoreAV rejects the file before any decoder: an unsupported container, or a
codec outside the allowlist.

Rejected: HLS playlists and `ffconcat` files (the CVE-2016-1897 and
CVE-2021-3566 classes): the pinned FFmpeg refuses an HLS playlist named like
a video, `http` segments from a local playlist and unsafe `ffconcat` paths,
so they no longer reach the components those descriptions name.

Rejected: downloading published crash reproducers (no hash-stable,
license-clear media was found, `hostile/reproducers.json`) or writing
working exploits from patches (clean room, and not needed to show the
surface).

## The demo

`tools/stage3-report/demo.sh FILE` runs, on the same file:

- FFmpeg as a black box in a sandbox: user, mount, network, process, IPC
  and host name namespaces of its own; a new session without a
  controlling terminal; a read-only root built from an allow list (`/usr`,
  `/etc`, `/bin`, `/sbin`, `/lib*`, the ffmpeg binary, a `/dev` of `null`,
  `zero`, `random` and `urandom`, an empty `/proc`, and the input file),
  so no user, service or session data, socket, terminal or other device of
  the host is in it; an empty environment; no capabilities; resource limits
  (address space, CPU time, file size, process count) and a wall-clock
  timeout. It prints what FFmpeg detected and that it decoded frames
  (`ffmpeg -i FILE -f null -`);
- `coreav probe --strict` and `coreav check` with an upload policy: both
  reject the file, with the `coreav.error/1` or verdict object;

The sandbox uses `unshare` (no root needed); the demo refuses to run FFmpeg
when the sandbox cannot be set up or does not hold: a check inside it
finds a capability, a terminal, a writable path, a Unix socket, a
credential in the environment, a process, a shared memory segment, a
descriptor inherited beyond 0 to 2 (the setup closes the launcher's), the
host's name, or anything at the top of the root, in `/dev` or in `/tmp`
beyond the allow list. An allow list rather than masks over the host's file system: a mask
list misses whatever a host keeps elsewhere (`/workspaces`, `/data`, a
session's logs), and a masked directory that is a symlink leads around
it. The user's supplementary groups still apply inside the user namespace
(it cannot drop them), but no device beyond the four is in the root.

## Alternatives considered

- **Reusing the per-family corpus drivers** (`tools/mkv-adapter/corpus.py`,
  `tools/isobmff-adapter/corpus/`): the MP4/MOV one captures streams only,
  and they need the AWS CLI. One driver for both families, with packets,
  the MediaInfo capture in the same pass and the downloader of the remux
  measurements, keeps one method and one download per file.
- **Gating the report in CI**: the corpus needs credentials and about an
  hour; CI keeps gating the fixture and hostile parts on every change, and
  this report is the release evidence.
